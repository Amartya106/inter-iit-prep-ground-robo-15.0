## Phase 1 and 2, getting the basics working (E1-E8)

**E1, PPO phase 1.** Just reaching, no peg. 1.5M steps, got 1.00 success straight away. Easy.

**E2, TQC phase 1.** Wanted to compare an off-policy algorithm. 0.6M steps, 0.935 success. Also fine, but TQC turned out to be slow on this CPU (more on that below).

**E3, PPO phase 2, early attempt.** Warm started from phase 1, got interrupted at 0.8M steps. 0.00 success, grasp failure 0.997, it basically never went near the peg.

**E4, TQC phase 2, "the gamble."** Tried off-policy again for phase 2, warm started from TQC phase 1, 2M step budget. Killed it at 0.96M once it plateaued. 0.01 success, grasp failure stuck around 0.82, reward flat around -3. Also only running 120-330 steps/s, so the full 2M would've taken forever anyway.

**E5, diagnosis.** Wrote `diagnose_phase2.py` to actually figure out what's going wrong instead of guessing. Cold start: the arm stalls a median 27cm from the peg, only 7.5% ever get within grasping range. Pre-grasped ablation: 16.7% success, and only 38% actually release the peg at the target. So two separate problems: it can't approach, and it can't release properly either.

**E6, PPO phase 2, fallback iter 1.** Kept the phase 1 warm start, added reward shaping and a grasp curriculum annealing 0.6 to 0, bumped ent_coef. Killed at 2.0M of 3M. 0.00 success, collapsed to grasp failure 0.998 right when the curriculum finished annealing. Never escaped the "reach toward goal_pos" habit it learned in phase 1.

**E7, PPO phase 2, fallback iter 2, SOLVED.** Dropped the warm start entirely, trained from scratch with the same shaping, curriculum 0.7 to 0 over 70%, higher learning rate. 3.0M steps, 0.995 success. Reward went from -11 to +63. Cold start diagnostic: 99.3% success, 1.9cm mean distance to peg, 100% grasp rate, 37 steps average. This is the one that worked.

**E8, demo/BC backstop (not needed in the end).** Built a scripted IK expert, collected demos, tried behavior cloning as a fallback in case E7 hadn't worked. Expert hit 80% success, 28,846 demo transitions collected, BC validation MSE 0.038 but 0% eval success (the classic covariate shift problem with pure BC). Didn't need it since E7 already solved phase 2, kept the code around just in case.

## Phase 3, the obstacle-avoidance grind (E9-E27)

**E9, PPO phase 3.** Warm started from E7, added 2-5 random obstacles, made collision count as failure. 2.5M steps, 0.515 success, 0.28 collision. Partial, the phase 2 policy had never seen an obstacle so it's slow to learn avoidance.

**E10, PPO phase 4, first attempt.** Warm started from E9, added the actual insertion task (xy under 1cm, tilt under 10 degrees, 3cm deep, held for 10 steps) plus obstacles. 4.0M steps, 0.015 success, 0.42 collision, insertion depth basically 0. Did not converge, this is way too much for PPO in this budget with no dedicated fixes. This 0.015/depth-basically-zero number is going to show up again and again for a long time.

**E11, phase 5, planned then killed.** Was going to warm start from E10 for dynamics generalization, but E10 never converged so a warm start from it means nothing. Didn't run it then (though see E62 way below, evaluating an existing checkpoint under phase 5 conditions doesn't actually need a phase-5-trained policy).

**E12, PPO phase 3, soft warm-start A/B.** Tried `--soft-warm-start` (reinit the value net, reset optimizer, reset log_std, keep the policy net) against E9. 2.5M steps, 0.475 success, 0.255 collision. Basically the same as E9, no real gain. The phase 2 to phase 3 transfer is mostly positive already so softening it doesn't help or hurt much. Legit null result.

**E13, PPO phase 3, Track A.** Added dense obstacle-repulsion shaping (penalty inside 12cm of the nearest obstacle) plus an obstacle-count curriculum ramping 0-1 up to 2-5 obstacles over half of training. 2.5M steps, 0.50 success, collision down to 0.19 from E9's 0.28. Mixed result: the repulsion shaping clearly worked for collision, but success stayed flat. Grasp failure was 0.72, high enough that whatever we gained on avoidance got offset somewhere else, probably obstacles getting in the way of the approach itself.

**E14, Track B demos for phase 3.** Extended the scripted expert with obstacle-avoidance steering, collected 800 episodes, 55% expert success (438/800, 25,628 transitions). Lower than phase 2's 80% as expected, obstacles are harder for a scripted controller too.

**E15, BC pretrain on phase 3 demos.** Trained 40 epochs on E14's data, validation MSE 0.051. Comparable to phase 2's 0.038, healthy convergence.

**E16, PPO phase 4, Track A v1.** Added a pre-aligned start curriculum (peg pre-grasped, positioned above the hole, annealed 0.6 to 0) plus a widened shaping-only depth gate. 4.0M steps, 0.015 success (same as E10), collision improved to 0.26, insert depth still 0.0009. Real null result on the metric that matters. I ran a 40-episode diagnostic on the trained policy: 89% of grasped episodes get within 10cm of the hole XY, so transit and align are fine, but max depth was exactly 0.00cm in all 40 episodes. The policy learns to hover aligned and never actually commits to pushing down. My read: the continuous depth reward is too weak against the shaped cost of a rim-contact disturbance during a real attempt. This is what led to E17.

**E17, PPO phase 4, Track A v2.** Added a one-time bonus for each new centimeter of real insertion depth reached, on top of E16. 4.0M steps, same 0.015 success, insert depth still bit-for-bit 0.0009. Second null result on the same metric, even though the bonus verifiably fired correctly and training-time reward climbed into positive territory for the first time. My working theory at this point: the pre-aligned curriculum starts the peg above the hole, never inside it, so the policy has literally never experienced what pushing through the 3mm bore feels like. No reward shape can push a motion that's never been sampled. Paused phase 4 here.

**E18, Track B, RL fine-tune from BC checkpoint.** Fine-tuned E15's BC model with RL instead of warm-starting from an RL policy. 2.5M steps, 0.0 success, grasp failure 0.997. Track A (E13, 0.50) clearly beats this. Demos help diagnosis and shaping more than they help as an actual warm start once a decent policy already exists.

**E19, PPO phase 3, Run A, grasp-miss penalty.** Added a small penalty for closing the gripper too far from the peg to actually grasp it, motivated by E13's 0.72 grasp failure rate. Warm started from E13. 2.5M steps, 0.71 success (up from 0.50!), collision 0.22, mean steps dropped to 109.5 from 191.9. Big real win, but not for the reason I expected: grasp failure rate barely moved. What actually changed is episode length nearly halved, the penalty seems to push the policy to commit or bail faster instead of hovering indecisively near the peg.

**E20, PPO phase 3, Run B, grasp-trigger curriculum added.** Same as E19 plus a curriculum that widens the grasp catch radius early and anneals it down. 2.5M steps, 0.73 success, basically a tie with E19 (noise at n=200 is about 3.2 points). Grasp failure actually got slightly worse across baseline to E19 to E20. The curriculum added nothing measurable. E19 stays the simpler, recommended version.

**E21, PPO phase 3, Run C.** Expanded obstacle-distance checking to all 7 arm links (not just the end effector), and made collision/repulsion penalties depend on whether the peg is being carried. 2.5M steps, 0.685 success, collision 0.20. Statistically the same as E19/E20 despite a well-targeted fix. A follow-up diagnostic found collisions are overwhelmingly at the wrist/end-effector links, so the "elbow blind spot" this fix targeted wasn't actually a real contributor.

**E22, PPO phase 3, Run D, repulsion re-tune.** Tried lower repulsion weights than E21. 2.5M steps, 0.68 success, collision 0.22, basically tied with E21 despite a 7.5x swing in the weight. Repulsion weight in this range just isn't the sensitive parameter.

**E23, PPO phase 3, Run E, repulsion re-tune corrected.** Fixed a mistake in E22's weight and reran. 2.5M steps, 0.725 success but collision got WORSE (0.25, the worst of any phase 3 run so far). No clean trend across E21/E22/E23 at all, this looks like real run-to-run noise at a magnitude comparable to what I'm trying to tune.

**E24, PPO phase 3, Run F, danger-zone shaping suppression + collision terminal.** Two structural changes this time instead of another weight tweak: zero out the goal-approach shaping whenever any part of the arm is inside the danger radius (so cutting through obstacles for reward doesn't pay off), and make collision immediately end the episode instead of just marking it failed while letting it keep running. 2.5M steps, 0.765 success, collision down to 0.195, and mean steps dropped to 57.75, the fastest yet. First result in this whole thread that improves both success and collision at the same time, not a tradeoff. **New standing best for phase 3.**

**E25, PPO phase 3, Run G.** Targeted the dominant collision link (the wrist/end-effector) with a virtual inflated radius plus a velocity penalty on the wrist joints. 2.5M steps, 0.745 success, collision 0.205. Neither metric moved outside noise of E24, and the diagnostic showed the wrist link still dominates collisions at basically the same rate. Null result.

**E26, PPO phase 3, Run H, final attempt on this thread.** Changed the approach itself to stage through a hover point above the peg before descending, like the scripted expert does. 2.5M steps, 0.725 success, collision 0.23. Doesn't beat E24. But the wrist link's collision share stayed at basically 60% across three completely different attempts now (E24, E25, E26), which itself is the useful finding: this residual looks structural to the task, not something reward shaping can fix. Closed this thread here, E24 (0.765/0.195) stands as the phase 3 result going into phase 4.

**E27, does E24 just need more steps?** Continued E24's checkpoint for 2.5M more steps (5M cumulative). Got 0.695 success, slightly worse than E24's own 2.5M result. Confirms E24 is a genuine plateau at this budget, not a run that got cut off early.

## First real phase 4 attempts (E28-E30)

**E28, PPO phase 4, plain re-run warm started from the much stronger E24.** No other changes, isolating whether a better phase 3 base matters at all. 4.0M steps, 0.01 success, collision actually got worse (0.72), depth still bit-for-bit 0.0009. Striking result: a much better phase 3 policy (0.765 vs 0.515) makes zero difference to phase 4. Diagnostic confirmed the same thing again: 90% of grasped episodes get the peg within 10cm of the hole, but max depth is exactly 0.00cm across all 150 episodes. This isn't a warm-start-quality problem.

**E29, SAC phase 3, from scratch.** Added SAC support to test another off-policy algorithm, cold start (can't warm start SAC from a PPO checkpoint, different architecture). 1.0M steps, 0.0 success both for the final and best-by-reward checkpoint. Never cracked the grasp gate at all. Diagnostic: grasp only formed in 8/150 episodes (5%), versus PPO's typical 85-98%. Same story as TQC's earlier failure on phase 2 (E4), off-policy methods seem to struggle with this specific hard-exploration gated-grasp problem when starting cold.

**E30, PPO phase 4, reverse insertion-depth curriculum.** Built a curriculum starting some episodes already partially inserted, annealing that away over training. Also fixed a real IK bug found while building this (joint-limit violations in the teleport code). 5.0M steps, 0.01 success, depth still bit-for-bit 0.0009. Fifth independent confirmation of the same wall. Mid-training telemetry did show real movement while the curriculum was active, but it didn't survive the anneal back to zero. The policy learns to hold a peg already inserted, but not how to arrive there on its own.

## Splitting phase 4 into sub-tasks (E31-E54)

Around here I started trying a SeqPolicy-style decomposition (inspired by a paper on splitting pick/align/insert into separate policies): Task 1 is reach+grasp+align to a hover point above the hole, Task 2 is just the insertion itself starting pre-grasped.

**E31, Task 1 "align," first attempt.** Also fixed a real grasp-geometry bug here: the peg was grasped rigidly at its center, which physically prevented real insertion depth since the flange would need to sit inside solid ring geometry. Fixed with a grasp offset near the peg's top. 2.0M steps, 0.0 success, grasp failure 0.93. Traced it: the policy cycles grasp-drop-grasp-drop every 1-2 steps, one episode had 289 grasp attempts and all 289 failed to hold. The new grasp offset shifted the post-grasp peg position and the warm-started policy never adapted, since there was no curriculum to bootstrap re-adaptation.

**E32, Task 1 v2.** Added a grasp curriculum to bootstrap holding under the new offset. 2.0M steps, still 0.0 success, grasp failure 0.919, basically unchanged from E31. The curriculum bootstrap didn't fix it. I checked directly whether the grasp constraint itself was physically stable (held it with zero policy input for 60 steps, stayed bounded and fine), so this confirms it's the policy's control behavior, not a physics bug. Task 1 is 0-for-2 on this specific problem, Task 2 remains unaffected and more promising.

**E33, Task 2 "insert," first attempt.** Every episode starts already grasped and aligned right in the insertion zone, with a curriculum on how much free starting depth is given. 2.5M steps, 0.025 success (5/200), depth 0.00314, tilt 8.41 degrees, grasp failure 0.389. **First nonzero result in a formal eval anywhere in phase 4's history.** Every prior attempt landed at exactly 0.0009 depth regardless of anything else tried, and this is 3.4x that. Still modest (2.5% success), but it's a genuine, reproducible break in a wall that held through 5 independent attempts.

**E34, Task 1 from scratch (no warm start).** Wanted to see if a fresh policy would avoid the grasp-offset adaptation problem entirely. Killed by me at 4.1M of 5.0M once the trend was clear. Grasp failure climbed to 0.99+, collision to 0.98-0.99, worse than either warm-started attempt. Confirms it's not a warm-start-adaptation problem, cold start is strictly harder here.

**E35, Task 1 v3, the actual fix.** Exempted Task 1 specifically from the grasp offset (it never needed it, Task 1 has no depth requirement at all). 2.0M steps, still 0.0 success, but grasp failure dropped to 0.723 from 0.92-0.93. Real, substantial improvement, just not enough to clear the tight alignment bar (xy under 1cm AND tilt under 10 degrees AND grasped, held for 10 steps). Task 1 is now a partially-solved problem, not a wall.

**E36, Task 1 v4, continued E35 for 4M more steps.** Testing whether E35 was still improving when its budget ran out. Result: 0.0 success, grasp failure 0.714, basically identical to E35. Plateaued, not still improving. 4x the extra budget did nothing.

**E37, Task 2 v2, continued E33 plus forearm repulsion shaping.** 2.5M more steps (5M cumulative), targeting the forearm collision problem E33's diagnostic found. 0.02 success, depth 0.00252, basically flat versus E33, not improved. Neither more budget nor this specific shaping addition compounds on E33's original gain. Grasp failure looked better (0.406) but that's likely just favorable variance.

**E38, composed end-to-end eval, Task1(E36) into Task2(E37).** Ran Task 1 until its own success condition fires or time runs out, then hands off to Task 2. 0.000 overall success. Since Task 1 alone was already 0/200, the composed pipeline never gets a real hand-off at all, everything just runs out Task 1's clock. This confirms the pipeline is fully blocked on Task 1 clearing its own bar.

**E39, composed eval, raw E24 as stage 1 instead.** Same idea, looser xy threshold hand-off. Got 12.5% hand-off rate, still 0 successes, depth barely moved off zero. Confirmed Task 2 can't handle more than about 1.5cm of hand-off misalignment, regardless of which Task 2 checkpoint it's paired with.

**E40, Task 1 v5, explicit grasp-drop penalty.** Added a direct penalty on the exact moment a grasp releases. Fresh warm start from E24. 2.0M steps, 0.0 success, but collision hit 0.45, the best Task 1 result so far. Grasp failure looked worse (0.897) but a per-episode trace showed this number is misleading: once the policy DOES grasp, toggling dropped way down (a real win for hold stability), but in 2/8 traced episodes it never committed to grasping at all, hovering near the peg forever instead. The penalty fixed one problem and created a milder version of a different one (grasp-commitment aversion).

**E41, Task 1 v6, arm-jitter penalty + softened xy pull.** Added a penalty for jittery arm motion while holding the peg, and annealed the approach reward's pull strength down over training. 2.0M steps, 0.0 success, collision 0.30, best Task 1 result yet. A 150-episode diagnostic versus E40: ever-grasped went 52% to 65%, clean single-grasp episodes 42% to 64%, real broad improvement on stability. But alignment precision among grasped episodes got slightly worse. Bottleneck shifted from "erratic holding" (mostly fixed) to "imprecise settling" (not fixed).

**E42, Task 1 v7, three changes combined.** Added a settle bonus, shortened the anneal, and doubled the approach bonuses, all stacked on top of E40/E41. 2.0M steps, 0.0 success, grasp failure 0.936, the worst of the whole series. Comprehensive regression, not the narrow "one issue persists" pattern I expected. Combining three untested changes in one run made it impossible to tell which one caused it, which is exactly the risk of doing that. E41 reinstated as the standing best.

**E43, Task 1 v8a, "settle-only," clean isolation.** Just the settle bonus added to E41's exact recipe, nothing else changed. 2.0M steps, 0.0 success, collision 0.645. Turns out the settle bonus ALONE reproduces almost all of E42's regression, overturning my E42 hypothesis (it wasn't the doubled bonuses or the faster anneal). I checked the reward code directly and confirmed the settle bonus strictly requires an actual grasp plus alignment, so it's not a "reward hovering" loophole. My best guess is the bonus is uncapped and creates a steep reward cliff right at the hold threshold. Not fully pinned down. E41 stays the best.

**E44, Task 1 v8b, drop-penalty anneal.** Same base as E43 plus ramping the drop penalty up slowly instead of fixing it from step 0. 2.0M steps, 0.0 success, collision 0.75, worst of the three v8 variants. The softer-early-penalty idea didn't pay off.

**E45, Task 1 v8c, linger penalty.** Same base as E43/E44 plus a penalty that grows for every step spent near the peg without grasping. 2.0M steps, 0.0 success, collision 0.35, best toggle-cleanliness and collision of the v8 batch. But grasp attempts per episode jumped to 104.3 with 103.3 of those failing, the policy rushes into badly-timed attempts instead of hovering forever. Trades one problem for another. None of the three v8 variants beats E41 outright.

**E46, GAIL instead of reward shaping.** Tried adversarial imitation, harvesting E24's own successful rollouts as free expert demos. 1.0M steps, 0.0 success, collision 0.63. Classic discriminator collapse: it pinned at 100% accuracy separating expert from generated data for most of training, so the generator got basically no useful gradient. Third time now that imitation learning has underperformed reward-shaped RL on this project (phase 2 BC, phase 3 E18, now this).

**E47, Task 2 v3, hand-off-robustness jitter training.** Added random xy/tilt jitter to Task 2's starting position, targeting E38/E39's finding about hand-off sensitivity. Also fixed a real IK convergence bug in the teleport code. 2.5M steps, 0.02 success, depth 0.00296. Statistically the same as E33/E37 on the isolated eval, which makes sense, the isolated eval always starts near-exact so it can't show the actual improvement (robustness to imprecise hand-off). The real test would be a composed eval with a realistic hand-off, which I didn't get to before shifting focus.

**E48, PPO phase 3, generalized arm-jitter penalty.** Generalized E41's jitter penalty to apply during ANY task, not just phase 4's align task, and warm started from E24 using the same recipe that produced E24. 2.5M steps, 0.71 success, worse than E24's 0.765. Real regression, predicted correctly from the training trajectory before the eval even landed: it started strong right after the warm start, degraded through the middle, and only partially recovered. The penalty was built for phase 4's specific "reaches precision but doesn't sustain it" problem, and phase 3's carry task doesn't have that problem, so it just adds cost with nothing to trade for it.

I did a lot of extra digging on this one though. Formally evaluated a checkpoint from right before the visible breakdown (750k steps): 0.68 success, still worse than the final model. A full 10-checkpoint sweep showed every single checkpoint below E24. But a much finer sweep of the EARLY checkpoints (every about 1-10k steps) told a different story: there's a real dip right after the warm start, then a genuine RECOVERY that peaks past E24 around step 30-40k, then decay into the worse plateau that persists for the rest of the 2.5M budget. The 40k checkpoint hit 0.80 success, 0.175 collision, actually beating E24.

I initially adopted 40k as the new standing best, but then found a genuine bug while trying to verify it with independent seeds: the eval episode sampler had hardcoded its RNG regardless of what seed was passed in, so every eval up to this point had secretly been using the exact same fixed 200 episodes every time. Fixed it properly (old behavior preserved by default, so every prior number in this file stays valid). With the fix, ran E24 and the 40k checkpoint on 6 independent episode sets each: E24 averaged 0.749/0.214, 40k averaged 0.738/0.217. Statistically a tie (3 wins each), not a robust win for 40k. But the submission is graded on the standard fixed eval seed, and under that exact protocol 40k does beat E24 (0.80/0.175 vs 0.765/0.195). Kept the 40k checkpoint as `runs/phase3_ppo_best`, and flagged the multi-seed nuance honestly rather than hiding it.

**E49, Task 1b "descend" v1, replay-seeded curriculum.** Split Task 1 further: episodes start pre-grasped at a random height above the hole and need to descend smoothly in. Also seeded 30% of training episodes from an exact recorded near-success state. Warm started from `phase3_ppo_best`. 2.0M steps, 0.0 success, collision 0.805, depth exactly 0. Flat null on formal eval despite real-looking training telemetry throughout. Same lesson as E48: training-time rolling stats don't predict the deterministic held-out eval. Collision is notably worse than anything else tried, probably because this sub-task starts already close to obstacles with less room to maneuver.

**E50, Task 1b v2, model-based dreaming added.** Built a small learned dynamics model and a callback that branches synthetic rollouts from real states during training, adding them to the PPO buffer. Verified the mechanism works correctly with a direct smoke test before using it for real. 2.0M steps, 0.0 success, collision 0.82, depth exactly 0. Same null as E49 despite training telemetry that looked even better this time. Reinforces the same lesson a second time: rolling training stats aren't a reliable preview of the real eval, on any variant of this task.

**Bugfix, obstacle keepout around the hole was too small.** I dug into why descend_only's collision rate was so much higher than phase 3's, and found obstacles were only kept 10cm from the hole's center point, not accounting for the actual swept volume of the arm once it's positioned there. Very likely the same root cause behind Task 2's persistently high collision numbers too, something I'd been misattributing to "insertion is hard" rather than "some episodes are literally unwinnable." Fixed by giving the hole a much bigger exclusion radius (0.10m to 0.28m). Verified this cut the fraction of episodes starting within 15cm of an obstacle from 70% to 29%. Not a complete fix (still XY-only, 3D clearance can still fail in rare cases), but a real improvement. Didn't retroactively re-evaluate old checkpoints against it, they stay historically accurate for the code as it was.

**E51, the REAL full monolithic task, plus dreaming, on top of the keepout fix.** Not a sub-task this time, the actual cold-start reach-to-insert task that had been stuck at 0.0009 depth across five independent prior attempts. Built a fresh dynamics model on data collected from this exact task. 2.5M steps, 0.015 success, collision 0.425, **insert depth 0.00136**. First genuine nonzero movement on BOTH of phase 4's hardest stuck numbers, on the first attempt at this combined recipe. Collision is way better than any Task 2 or descend_only variant, strong evidence the keepout fix is real and load-bearing. Depth breaking the 0.0009 wall is the more exciting one. I can't cleanly separate how much came from the keepout fix versus the dreaming though, since both changed at once.

**E52, same as E51 but way more dreaming.** Cranked up how much of the training buffer is synthetic (about 9x more than E51). 2.5M steps, 0.01 success, collision 0.50, depth fell exactly BACK to 0.0009. More dreaming made things worse, not better. E51's genuine break didn't survive scaling it up. My guess is the dynamics model's own prediction error (about 94% of variance explained, real but not perfect) starts to matter more once it's supplying a bigger fraction of the signal.

**E53, same idea, 30% of the buffer synthetic exactly.** 2.5M steps, 0.015 success, collision 0.42 (basically tied with E51), but depth fell back to 0.0009 again. Second independent confirmation that scaling dreaming volume past E51's small amount erases the depth gain specifically, without buying anything else. E51 remains the best full-task result, and the only one of several dreaming variants that ever broke the depth wall.

**E54, multi-expert BC, raw checkpoint, no RL fine-tune.** Checked directly first whether grasp_failure_rate was even a fixable-by-combining-policies metric, decided it wasn't (it's dominated by how attempts get counted, not real skill), so redirected toward combining for `ever_grasped` instead. Distilled from three specialists' rollouts (align-only, insert-only, and the full task) into one BC policy. Found and fixed a real bug along the way: a handful of high-force collision frames were dominating the observation normalization stats and crushing the everyday force signal, fixed with percentile-clipped stats. 0 RL steps (BC only, an RL fine-tune attempt hit an unexplained throughput issue and got killed rather than let it run indefinitely). 0.015 success, collision **0.23**, the best collision result of the entire phase 4 investigation so far, via pure imitation with zero RL correction. Depth landed back at 0.0009 though, not a clean sweep.

## The pivot: measuring the environment instead of tuning the learner (E55-E69)

At this point success had been stuck around 1.5-2% forever no matter what I threw at the reward or the learning setup, so I stopped and tried to find what's actually possible here

**E55, oracle ceiling measurement.** Ran the existing scripted IK expert (perfect information, no exploration problem at all) cold start on the eval set with detailed per-stage funnel tracking. **Oracle success: 0.020.** Same about 2% every trained policy had been topping out at. So the learner was never the bottleneck. The funnel showed grasp works fine (0.670), align works fine too (conditional 0.806), but then **entering the hole once aligned collapses to 10.2% conditional.** 90% of the failure is right there, at getting an already-aligned peg across the rim. Ring contact diagnostics showed pegs landing on the rim at a mean 4.6cm off center (not the 1cm tolerance opening) and getting stuck there for 120 steps on average. This looks like a geometry problem (3mm clearance, sharp square rim, rigid grasp, no chamfer), not something reward shaping or exploration can fix.

**Bugfix, IK solver was silently broken, plus a second convergence bug.** Found while building E55's harness. The bounded IK solver defaulted to only 20 iterations with a strong pull back to a rest pose, and measured directly it was landing 14-36cm off target. This meant Task 2's "start already inserted" curriculum never actually started inserted, on every single reset, for the entire E33/E37/E47 investigation. Also found the teleport retry loop wasn't resetting to a clean pose between attempts and was only checking XY convergence, missing bad Z convergence. Fixed both. Note: this doesn't touch E55's oracle number since the scripted expert uses its own live IK, not this teleport code, so the oracle measurement stands. It does mean some of E33/E37/E47's exact starting conditions were less clean than intended, though their results stay on record as accurate for the code as it was then.

**E56, environment-fix ablation, oracle-gated.** The plan was: don't retrain RL until the oracle clears about 40%. Tried four fixes one at a time: a chamfer funnel above the hole, a compliant (finite-force) grasp instead of rigid, a fine-control speed taper near the hole, and a joint velocity cap (this one fixed a real bug where an ungrasped peg could get launched at high speed from contact solver stiffness). Result: **all four, alone and combined, kept oracle success at 0.020.** The entering-the-hole bottleneck barely moved (7.8-10.9% across every variant). None of the four tested levers is the dominant bottleneck. The 40% gate was not met.

But I found something else while tracing a good-alignment episode that still failed to enter: **it's peg TILT, not xy precision, that's actually blocking entry.** The scripted expert locks in whatever orientation IK happened to produce and never corrects it, and I measured 75% of episodes carrying more than 10 degrees of tilt at that point (median 18.4 degrees). A peg tilted 30 degrees just physically doesn't fit through a 3mm clearance regardless of how good the XY is. Tried forcing the expert to true-vertical at two different points in its state machine, both broke something else (grasping, or alignment), and reverted both. Also fixed a genuine bug found in the process (a stale orientation variable never got cleared between episodes). Didn't chase the tilt fix further in the oracle itself, that's not the right place, flagged it as the key input for the reward design going forward instead.

**E57, fixed-env retrain, warm started from E51.** Applied E56's three non-regressive fixes (chamfer, compliant grasp, velocity cap), raised the tilt penalty weight, and added a curriculum that adjusts based on rolling train success instead of a fixed schedule. 2.5M steps. Final checkpoint: 0.015 success, collision 0.36, depth back to 0.0009 (lost E51's break). Best checkpoint by eval reward: same success, worse collision (0.495). Mixed, not a clean win, reported honestly as such. The training curve showed real instability late in the run that I think confounds this comparison (an unaddressed learning-rate/target_kl issue). E51 stays the best full-task result.

**E58, compliant scripted expert.** Tried giving the scripted expert gradual reorientation (slerp toward vertical instead of an instant snap) plus a spiral search when insertion depth stalls. Tried force feedback first but the wrist force signal turned out to be dominated by motion noise, not contact, so used depth-stall detection instead. N=100 test: grasp got slightly better, but alignment got WORSE (the gradual reorientation swings the rigidly-held peg through an arc as it corrects), entering the hole stayed about the same, success unchanged at 0.020. The spiral search genuinely helped (cut worst-case stuck time 5x), reorientation is a real tradeoff not a bug. This is exactly what E56 predicted: a solve-once-and-freeze IK controller can't converge position and orientation together the way a continuously-trained policy can.

**E59, MPC (CEM) expert demos over a learned dynamics model.** A genuinely different kind of demonstrator: sample many candidate action sequences, roll them through a learned model, score them, commit to only the best first action. Swept the hyperparameters first and found the refinement passes matter way more than horizon length or candidate count. Best setting reached 60% ever-grasped with real depth progress in the verification sweep. Full-scale collection (60 episodes): 2% success, same ceiling as everything else. So MPC CAN find depth progress the scripted controller couldn't in short verification runs, but doesn't beat the ceiling at real scale. 228 transitions collected, too few to train a standalone BC policy on, not attempted. Also found and fixed a mundane throughput issue (buffered stdout hiding progress, plus too many background jobs competing for the same cores).

**E60, HER-relabeled demos.** Tried Hindsight Experience Replay, but scoped it honestly to align-only (relabeling "target position" isn't physically valid for insertion, there's no hole wherever the peg happened to end up). Rolled the compliant expert through full episodes and relabeled grasped segments with future achieved positions as goals. Validation MSE hit 0.017, the lowest of any BC run so far. Evaluated on align-only cold start: 0.000 success. Traced why: HER relabeling only ever touches GRASPED segments, so the policy literally never saw an ungrasped observation in training, and the real eval always starts ungrasped. The low validation loss was a trap, not a sign of quality, it fit an easy narrow slice of state space that the real eval never visits the same way.

**E61, combine IK + MPC demos.** After three single-source demo attempts each showing a partial result, combined E58 and E59's sources properly (collected fresh with consistent raw observations, one shared normalization fit at the end, following the same pattern that worked for E54). 1,594 transitions total. Evaluated on the full task: 0.015 success (ties the standing best), but collision (0.465) worse than both E51 and E54, depth back at the historic wall. Ties one axis, loses on the others. E54's much bigger 81k-transition dataset (from RL-trained specialists, not raw IK/MPC rollouts) is doing real work that this smaller combined set doesn't replicate.

**E62, phase 5 generalization, run for the first time.** This had existed in the codebase the whole time but never gotten used, since the assumption was "phase 4 never converged so there's nothing to generalize." But evaluating an existing checkpoint doesn't need a phase-5-trained policy. Ran E51 under both in-distribution and unseen-dynamics conditions. In-dist reproduced bit-identical (0.015/0.425/0.00136). Unseen dynamics: success unchanged (0.015), but collision jumped to 0.555 (+31% relative), and depth fell back to the 0.0009 wall. Real, clean generalization result: success holds flat (the about 1.5% ceiling seems insensitive to dynamics shifts, consistent with the bottleneck being kinematic/tilt-related, not dynamics-related), but collision clearly degrades under unseen conditions.

**Bugfix, two real eval-harness bugs found preparing E62/E63.** The documented way to get a phase 5 comparison (`--conditions in_dist,unseen_dynamics`) never actually worked, the code only ever branched on noise conditions, so that invocation silently produced two identical rows. Fixed the docs to the two-separate-calls workflow that actually works. Second bug: the noise sweep's own zero-noise baseline still applied a small forced peg impulse due to a `max(2.0...)` floor, so there was never a genuinely clean baseline row. Fixed by removing the floor. Verified neither fix changes any existing in-distribution number.

**E63, phase 6 stress test, run for the first time.** Same E51 checkpoint, noise sweep from 0 to 0.08 sigma (additive noise on obs/action plus periodic peg impulses). Success stayed flat at 0.015 across every level (a floor effect, not evidence of robustness, there's not much room to fall further from an already-98.5%-failing policy). **Collision degrades gracefully**, a smooth monotonic climb from 0.425 to 0.690. But **the rare fine behaviors are brittle**: E51's headline depth break (0.00136) and its tightest tilt control both evaporate at the smallest tested noise level and never come back. Coarse, common behaviors degrade gracefully, the one genuinely rare hard-won behavior doesn't survive any noise at all.

**E64, relaxed success metric re-eval.** Wanted to check whether the about 1.5% ceiling was really about the success predicate's own strictness. Loosened depth/xy/tilt/hold requirements substantially and re-ran E51 on phases 4, 5, and 6. Success moved by exactly 0.000 everywhere. Clean negative, and informative: confirms the bottleneck really is "does the peg cross the rim at all," not "how precisely does it finish." Once it's in, E56's funnel already showed it usually goes all the way, so loosening the finish line can't unlock episodes that never entered in the first place.

**E65, peg-frame FK control for the scripted expert.** Found a real bookkeeping bug: the expert was aiming the flange at one target while separately slerping a different orientation the SAME step, and these two targets disagreed, producing up to 2.25cm of peg drift at the diagnosed tilt angles. Built a proper fix that computes the flange target from the desired peg pose directly, so position and orientation can't disagree. 3-way comparison (no reorientation, the old slerp approach, the new peg-frame approach), N=100 each. Alignment precision with the new approach (46% of grasped episodes under the 3.5mm gate) is dramatically better than the old slerp approach (19%). But entering the hole didn't improve, and here's the surprise: the expert's own AND-gated commit condition (xy AND height AND tilt all satisfied at once) never fired even once for either reorientation scheme, in 100 episodes each. Whatever entries did happen for these modes happened WITHOUT a controlled expert-driven descent, likely an ungrasped peg tumbling near the hole (the insertion success check never verifies the peg is actually still grasped, a pre-existing quirk this run didn't introduce). Real bug, real fix, but the broader claim that fixing it clears the ceiling isn't supported.

**E66, follow-up, why did the commit gate never fire?** Traced it step by step and found two more real bugs. First, the three commit conditions (xy, height, tilt) each individually cross their bars but never at the same timestep under active reorientation, since gentle continuous motion means the minima land at different moments. Loosened the gate to match what the environment's actual success predicate requires. Second, once episodes could commit at all, I found the insertion target was jumping instantly 12cm the moment insertion starts, a discontinuous commanded jump that spikes tilt and xy error within 2-3 steps. Fixed with a smooth ramp, applied to all reorientation modes since this one's structural, not reorientation-specific. Re-ran the 3-way comparison with both fixes. Peg-frame's tilt at commit is now excellent (2.3 degrees mean, versus the original 18-21 degrees), which DOES fully fix depth-once-entered (100% conditional, 3/3), but entering the hole in the first place is actually WORSE than the simplest mode now (5.9% vs 18.0% conditional). A longer trace of a committed episode showed xy error drifting slowly from under 1cm to 5-6cm over the about 60-step descent even with tilt perfectly controlled. So fixing tilt-at-commit does NOT fix entry rate, refuting my original "tilt magnitude is the dominant blocker" read. What actually predicts success once entered is tilt. What blocks entering in the first place is this newly found slow xy drift, not yet root-caused.

**E67, keypoint docking reward, PPO retrain.** Tried a fused position+orientation reward term (matching keypoints on the peg rim against keypoints on the bore, rotation-invariant) as an alternative to the separate xy/tilt terms, warm started from E51. Ran two parallel arms, one with a KL divergence guard (`target_kl`) and one without, since a previous run (E57) had shown signs of unguarded KL drift. 2.5M steps each. Both arms tied E51 on success (0.015) and both lost the depth-wall break. But the guard ablation was decisive: without it, KL divergence and action noise climbed continuously for the whole run and never plateaued, landing on worse collision (0.530, +25% relative) than the guarded arm (0.435, near E51's own baseline). Recommend using `target_kl` on any future PPO warm-start retrain in this codebase. The keypoint reward itself doesn't move the ceiling, the ceiling seems robust to reward reformulation as a category of fix at this point.

**E68, root-causing E66's xy drift.** Tried three candidate fixes: better IK convergence settings, a slower descent ramp, and explicit proportional feedback correcting toward the hole center using the actually-measured peg position. N=100 each, plus a direct step-by-step trace at three different feedback gains. None of the three fixed it. The feedback gain result is the most telling: quadrupling the correction strength made literally no improvement to the drift trajectory when traced directly, which rules out "the target isn't being actively corrected" as the mechanism. The slower ramp made things WORSE. This points away from a simple bias or timing issue and toward something more structural, most likely the redundant 7th DOF of this arm wandering through its null space in a way that correcting the target position can't reach. Per the plan, didn't retrain RL since the oracle itself never moved. Five real bugs found and fixed across E65/E66/E68 without moving the headline number once. Complete, honest diagnosis at this point, not an unfinished investigation.

**E69, UR5 (6-DOF) port, direct test of the null-space hypothesis.** Built an isolated UR5 package reusing the exact same reward function and episode sampler unmodified, just swapping the robot. Fixed three integration bugs along the way (a URDF joint-indexing offset, some hardcoded KUKA-sized arrays in the reward function, and a bad initial rest pose). Ran the same 3-way reorientation comparison, N=100 each. **UR5, no reorientation: entering the hole conditional on alignment is 0.788, versus KUKA's 0.153-0.180 across every mode tried.** UR5 slerp mode: **success 0.130 (13/100)**, 6.5x KUKA's ceiling that held flat across every single one of the 68 prior experiments in this project. Decisive support for the redundant-DOF hypothesis. One genuine surprise though: UR5's own peg-frame mode (the most sophisticated one, the one that fixed KUKA's tilt problem) actually underperforms UR5's simpler slerp mode here, and ties KUKA's flat ceiling instead of clearing it. My best read: peg-frame's tuning was reverse-engineered specifically to work around KUKA's redundant-DOF wander, and that machinery might just be unnecessary complexity on an arm that doesn't have the problem in the first place. The right reorientation strategy looks arm-dependent, porting a KUKA-tuned fix wholesale to a different arm isn't automatically safe. This result is strong enough to justify a real RL retrain on UR5 as a follow-up.

## Going all in on KUKA phase 4 (E70 onward)

After E69 confirmed the redundant 7th DOF was a real contributor to KUKA's entry-rate problem, I went back to KUKA specifically and did a much deeper pass, acting as if I were a senior RL researcher asked to find 3 distinct hypotheses for why the agent wasn't learning, focused on reward shaping, observation completeness, and gradient scaling.

**H1, exploration noise ratchet.** Found that PPO's entropy bonus puts a constant, unopposed gradient on the policy's log_std, and this gets inherited verbatim across every warm start with nothing in phases 1-3's reward ever pushing back on it for the wrist joints specifically (since nothing before phase 4 cares about peg orientation). Measured it directly: log_std on the wrist joints balloons from about 1.0 after phase 2 to 7.7-245x that by various phase 4 checkpoints, while other joints stay flat or collapse. Built `LogStdBandClamp`, a two-sided clamp on log_std applied every training step (instead of fragile single ent_coef guessing), plus flags to reset log_std on a warm start.

**E70, phase 4 retrain with the log_std reset/clamp.** Full checkpoint sweep afterward, same pattern as everything else in this file. Didn't clear the ceiling on its own, this hypothesis alone wasn't the whole story, but the mechanism itself is real and stays in the toolkit for later combined attempts.

**H2, reward dead zone.** Found that insertion depth was being measured from the peg's CENTER, not its TIP. With the peg's height being 8cm, this means the reward pays literally nothing for the first 4cm of real physical insertion. Fixed in the environment code (both KUKA and the UR5 port) to measure from the tip instead.

**H3, observation incompleteness.** The policy's observation vector was missing several fields that seem important for fine insertion control: peg tilt in radians, distance to the nearest point on the ring, a shaped depth signal, the vector from peg tip to hole, and ring contact/force. Added all of these, which widened the observation from 123 to 131 dimensions per frame (369 to 393 stacked). This meant every existing checkpoint's first layer no longer matched shape with a fresh model, so a plain warm start would just fail outright.

**Warm-start surgery.** Built `warm_start_pad()`, a function-preserving weight transplant: build a fresh model at the new wider width, copy the old checkpoint's weights into the matching sub-slices of each frame, zero-init only the new columns. Verified this is exact, not approximate: the old model on raw input and the new padded model on zero-padded input produce bit-identical output (checked via `torch.allclose` across 20 random trials).

**E73, insert-only retrain with the combined H2+H3 fixes plus warm-start-pad plus the log_std clamp.** This one actually worked. Full checkpoint sweep: **best checkpoint scored 0.040 success, 0.004 depth.** This is the best real result the entire KUKA phase 4 investigation has produced, roughly 2x the floor and 1.6x E33's original historical breakthrough.

**E74, same combined recipe on the REAL full monolithic task, gated on E73's result.** Null. Grasp failure sat around 1.0 for basically the entire run. The combined fix worked for the isolated insert sub-task but not once grasping has to happen cold from scratch first.

**E75, Align specialist, same combined recipe.** Also null, 0/200. This makes Align 0-for-12 historically across every attempt in this project so far.

**E76, full task retrain, added a critic reinit plus a higher noise floor on just the gripper dimension** (a plan v2 step, on the theory that the value net inherited from a different reward landscape was miscalibrated and actively hurting). I killed this one partway through at 54%. The critic genuinely got repaired (explained variance recovered fast, verified directly), but grasp failure stayed pinned near 1.0 regardless. Confirms the stale critic wasn't the (whole) problem either.

**E77, relaxed success definition plus a grasp curriculum, run to completion, dual checkpoint sweep afterward.** I tweaked what counts as success to be easier and disclosed that clearly, then retrained. Full 5M steps, 11 checkpoints, evaluated under BOTH the official predicate and the relaxed one. Both landed on **the exact same numbers everywhere**, success flat at 0.015, grasp failure sitting at 0.98-0.99 through the ENTIRE run, never recovering once. Collision actually got worse across checkpoints (0.26 up to 0.46). Relaxing the finish line didn't help at all, because the problem isn't precision, it's that grasping basically never happens. Complete, clean null. This closes out the "make success easier" angle as a real thing I tried, not just a theory.

**E78, normalization-mismatch fix, started then redirected.** I'd noticed no warm-start-pad run all session had ever actually loaded phase 3's fitted observation normalization stats, they were all using fresh mean-0/var-1 stats instead, while phase 3's real stats range enormously (variance from near-zero up to over 17,000 on some dimensions). Built a proper, verified, SB3-loadable padded VecNormalize carrying phase 3's real stats forward. Launched a retrain with it. Killed partway through on my own direction, to go try the utility-based RL paper instead (arXiv:2402.02665) rather than keep chasing this specific angle. Left as an open thread, not a completed test.

## Applying utility-based RL (arXiv:2402.02665)

The paper reframes RL reward design through an explicit multi-objective utility function instead of an implicit fixed linear weighted sum, which is exactly the structure this project's own reward already has. It's relevant here for a specific reason: the H2 dead-zone investigation had already found and numerically confirmed a real ridge in the existing reward, where hovering near the hole beats actually attempting descent by about 59x in expectation, because a bad outcome (a rim-clip disturbance) costs way more than a good outcome gains under the current linear scalarization.

Implemented two mechanisms from the paper, both new, both opt-in, both defaulting to today's exact behavior:

**Satisficing proximity** (the paper's section 4.4): instead of a continuously-scaled danger signal doing double duty as both a penalty and a shaping killswitch, make "safe enough" a flat zero-cost region and only suppress goal-approach shaping within a tighter sub-threshold of the real danger margin, not the whole thing.

**Risk-seeking depth** (section 4.2, generalizing risk-aware RL to the risk-seeking case): cap the penalty portion of the insertion reward (the xy-error and tilt cost) while genuinely attempting entry, leaving the depth bonus itself uncapped. A bounded-loss, unbounded-gain structure, the direct counter to the linear-scalarization ridge H2 found.

Verified numerically against the real reward function, not just "it runs": recomputed the exact hover-versus-attempt expected value comparison from the H2 ridge table. Hovering's advantage over attempting narrows from **59.4x to 16.6x**, a 72% reduction, with risk_seeking_depth turned on. Also ran `pytest`, 18/18 passing with both new flags at their default off, confirming nothing existing changed. Smoke tested both flags on the real simulator (not just the synthetic verification state) across both phases.

Wired both flags through `manipularl/env.py`, `manipularl/make_env.py`, and `train.py`, mirroring the existing pattern used for the other optional reward terms already in this codebase.

**Phase 3 satisficing retrain.** Warm started from `phase2_ppo`. ## E79: the grasp weld itself was corrupting orientation on every real grasp

After the utility-RL detour confirmed the blocker was upstream of insertion (grasp never happens, so no insertion-reward shape can matter), I went back to first principles instead of tuning further: why does `ever_grasped` sit at about 0-3% on the full cold-start task when the oracle grasps 67-71% of the time with the exact same environment?

**Root cause, found by reading `_form_grasp` (`manipularl/env.py`), not by more training.** Every real grasp, `_handle_grasp`'s cold-start path AND every teleport curriculum, goes through one function that welds the peg to the flange via `p.createConstraint(..., JOINT_FIXED, childFramePosition=[0,0,child_off])`, `child_off=_GRASP_OFFSET_Z` (0.035, "grasp near the peg's top, not its center") for `peg_in_hole`/non-`align_only`, `0.0` (center-snap) everywhere else. Both frame orientations were left at PyBullet's identity default. `JOINT_FIXED` with identity frame orientations constrains `child_orn == parent_orn` **regardless of `childFramePosition`**, so on every real cold grasp, with nothing in `_handle_grasp` controlling flange orientation at all (no contact check, no alignment gate, no velocity gate, just a 9cm sphere test), the peg got teleported and **force-rotated to the flange's arbitrary orientation** at the instant of grasp. The peg spawns 0-5.7deg from vertical (`randomization.py`, `peg_tilt drawn from U(0,0.10) rad`); this discarded that and substituted whatever the flange happened to be doing. This is the mechanism behind:
- **E56's measured 20-40deg grasp tilt**: not unfixable physics, a forced re-orientation to an uncontrolled value.
- **E31's GRASP<->DROP flicker** (289/289 failures): the 3.5cm positional teleport this same mechanism adds on top, when the offset was first introduced. E35 "fixed" it by exempting `align_only` back to `child_off=0.0`, but the full cold-start task kept running the exact configuration E31 had already proven causes near-100% grasp failure, for the rest of the project's history. The learner's `grasp_failure_rate=1.000` in every full-task run (E70-E78, the utility run) is that same signature, previously misattributed to exploration/reward/observation problems.
- The oracle (E55) surviving fine, because it drives the flange to a proper vertical pose via IK before closing the gripper. A real policy never controls for this, so it eats the bug on every attempt.
- The UR5 port (E69) reaching 0.788 enter-conditional **despite carrying the identical bug** (`manipularl_ur5/env.py`). The redundant-DOF finding is real, but it was never the whole story; this bug applied there too and UR5's own scripted approach evidently tolerates it better geometrically.

**The fix.** `_form_grasp` now branches on `child_off`. `child_off <= 0.0` (phases 1-3, `align_only`): byte-for-byte the old weld, unchanged, verified via `p.getConstraintInfo`, exact match to `(0,0,0)` + identity, no simulation stepping involved (`tests/test_env.py::test_grasp_weld_unaffected_for_pick_place`, parametrized over phases 1-3). `child_off > 0.0` (peg_in_hole, non-`align_only`): a **preserve-transform** weld: `childFramePosition`/`childFrameOrientation` are computed from the REAL flange and peg poses at grasp time (`peg_pose^-1 ∘ flange_pose`, via `p.invertTransform`/`p.multiplyTransforms`), so grasping never teleports or re-orients the peg; it welds wherever the gripper actually is. A **grasp-admissibility gate** replaces the old bare 9cm-sphere test for this branch only: the flange must already be within `[0.015, 0.055]` of the peg's own top (along the peg's body axis) and `<0.035` laterally, otherwise the attempt fails (counts as a normal grasp failure, same bookkeeping as "too far" always did). Without this, an ungoverned preserve-transform grasp from the peg's side could weld the flange level with the peg's center and make `insert_success_depth` physically unreachable again, which is the original, legitimate reason `_GRASP_OFFSET_Z` existed. This is a genuine tightening (disclosed): the oracle's own raw grasp rate on the SAME episodes dropped 71%->31%, since its scripted approach wasn't tuned for the new band. `_regrasp_with_offset` (the Task1->Task2 composed-eval hand-off) needed a matching redesign, since it used to rely on the old weld's teleport-on-reattach behavior to inject the offset "for free"; under preserve-transform it would have silently become a no-op (peg already zero-offset from Task 1, so the naive re-weld would just re-capture roughly identity). Redesigned to explicitly slide the peg along its OWN current axis (not world-z, not the flange's) so it meets the flange, preserving whatever alignment Task 1 already achieved instead of forcing either frame's orientation.

**Getting the math right took several wrong turns, which is its own finding about testing this kind of fix.** A first implementation (`invertTransform(flange)` composed with peg) looked identical to the correct one on paper and passed an initial reviewing pass, but was backwards, caught only because a permanent regression test (`getConstraintInfo`, zero-stepping, comparing what `_form_grasp` actually told PyBullet against an independently-derived transform) disagreed with the implementation by about 5cm. Every simulation-based probe attempted before that test existed (multi-step `stepSimulation()` loops, with the arm held via `resetJointState`, via soft `POSITION_CONTROL`, via IK-converged targets) produced misleading drift of anywhere from 15mm to 350mm, all traced, one at a time, to confounds in the probe itself (unreachable IK targets, the arm drifting under its own residual motor state with literally zero peg/gravity/constraint involved, confirmed independently at 0.1rad over 20 raw `stepSimulation()` calls, free-fall tumbling before a grasp trigger fired, and an out-of-workspace test peg interacting with `env.step()`'s own termination handling), never to the fix. The two checks that actually worked were an algebraic invariant (`peg_pose ∘ rel == flange_pose`, zero stepping, sub-micrometer/sub-arcsecond exact) and reading back `p.getConstraintInfo`'s own stored parameters, both fully deterministic, neither touching the physics stepper at all.

**Verification, cheap probes only, no training (that's the next decision, not yet taken).**
- `tests/test_env.py`: 22/22 (18 original + 4 new grasp-weld checks, phases 1-3 confirmed byte-identical, phase 4 confirmed to preserve the real transform, both deterministic/zero-stepping).
- `scripts/oracle_ceiling.py`, n=100 each, pre-fix vs post-fix, `--reorient-mode {none,slerp,pegframe}`:

Oracle success at 6% is still far below Phase 1-3's 80-99%+, and a trained POLICY reaching anywhere near even this new, higher oracle ceiling is untested and would additionally require learning the active-reorientation-during-descent behavior the `pegframe` condition needed, not just inheriting a corrected grasp. Whether to spend the training compute to find out is a separate, not-yet-taken decision.

## E80: first two training attempts against E79 both stalled, diagnosed why, third attempt in progress

The decision from E79 (spend the training compute) was taken. Two runs launched in parallel, same seed, 5M steps each, PPO, from scratch (no warm start, matching E7's own precedent for this exact grasp-collapse symptom):

- **R1** (`configs/ppo_phase4_scratch_graspcurr.yaml`, `runs/phase4_scratch_graspcurr`): full task, `grasp_curriculum: 0.7` annealed over 60% of training, phase 2's proven E7 recipe transposed to phase 4. No full-task phase-4 config had ever used a grasp curriculum before this.
- **R2** (`configs/ppo_phase4_scratch_wideadmit.yaml`, `runs/phase4_scratch_wideadmit`): identical to R1 plus a widened grasp-admissibility band (`grasp_admit_axial_hi` 0.055->0.075m, `grasp_admit_lateral` 0.035->0.05m, new opt-in `PhaseConfig` fields, `manipularl/configs.py`, read in `env._handle_grasp`, default unchanged for every other config). Rationale: `grasp_shape`'s dense reward (`rewards.py`, `near = exp(-d_ee_peg/0.08)`) peaks at the peg's CENTER, which the new admissibility gate rejects. Widening the band tests whether that mismatch was the binding constraint.

**Result: both stalled.** `ever_grasped_rate` at 1.0M/1.5M/5.0M(final), 200-episode formal eval:

| | 1.0M | 1.5M | 5.0M (final) | success (final) |
|---|---|---|---|---|
| R1 | 0.000 | 0.000 | 0.005 | 0.015 |
| R2 | 0.000 | 0.000 | 0.000 | 0.015 |

Per the pre-committed decision criteria: both under the 0.15 kill bar at 1.5M means the admissibility band was NOT the binding constraint (R2's genuinely wider band made zero difference, if anything slightly worse): "the blocker is upstream of E79 again," and the right move is another cheap probe before more training compute, not immediately trying a third training recipe blind.

**Diagnosed, not guessed.** `scripts/diagnose_phase4.py --run runs/phase4_scratch_graspcurr --episodes 100`: **85% of episodes collide before ever grasping**, and a direct trace of closest-approach-to-peg across 30 real eval episodes found only **23% of episodes ever get within the 9cm grasp-trigger radius at all** (mean closest approach 19.6cm). Collision-terminal (`collision_is_failure=True`, phase 4 has 3 obstacles) is ending most episodes before the arm completes its approach. The grasp-shape/admissibility-band question from R2 is a real but second-order effect for the minority of episodes that DO get close; the dominant, first-order failure is that R1/R2's recipe asked a from-scratch policy to learn cold-start grasping AND obstacle avoidance simultaneously. No prior successful recipe in this project ever required that: phase 3's own progression (E13) solved grasp+carry FIRST (phase 2, zero obstacles) then added obstacles via warm start plus its own `obstacle_curriculum` (`ObstacleCountCurriculum`, `train.py`/`manipularl/callbacks.py`), proven infrastructure that was already built and simply never wired into any full-task phase-4 config before now.

**R3** (`configs/ppo_phase4_scratch_obstaclecurr.yaml`, `runs/phase4_scratch_obstaclecurr`): R1 plus `obstacle_curriculum: true, obstacle_curriculum_start: [0,1], obstacle_curriculum_frac: 0.5`, the exact mechanism and near-identical parameters E13 used to take phase 3 from 0.515/0.28 to 0.765/0.195. Admissibility band left at the E79 default (R2 already showed widening it doesn't help).

**R3 result: diverged, killed before completion.** `ever_grasped_rate` stayed at 0.000 throughout (same as R1/R2), but `collision_rate` at matched eval checkpoints got WORSE over training, monotonically and well past the point the obstacle curriculum finishes ramping (2.5M): 0.49 (1.0M) -> 0.67 (1.5M) -> 0.91 (3.0M) -> 0.91 (3.5M) -> 0.95 (4.0M), with mean episode length collapsing from 235 to 57 steps (of a 400-step max) over the same span. Sustained, not a transient dip at the curriculum-anneal boundary. Killed manually at about 4.1M/5M once the trend was unambiguous.

**Root cause of R3's divergence**: the dense grasp-approach reward (`rewards.py`, pure Euclidean distance to the peg's CENTER) is completely obstacle-blind. As the curriculum densifies obstacles, the policy has an increasingly confident straight-line gradient toward the peg that runs straight through them; PPO's on-policy updates can't cross that reward valley once the straight-line habit is established, so the policy gets MORE confidently wrong over training rather than discovering a detour ("moth to a flame"). Also identified: R1/R2/R3 all used `ent_coef: 0.008`, matching the proven ZERO-obstacle recipe (phase 2's own scratch config), but the recipe that actually solved obstacle avoidance (`configs/ppo_phase3.yaml`, E13) used the higher `ent_coef: 0.01`, and was warm-started from an already grasp-competent, zero-obstacle checkpoint rather than learning both skills from scratch simultaneously. R1/R2/R3 never warm-started specifically because the only available phase-3 source was trained under the OLD broken grasp weld (E79), reusing it would import a now-wrong habit.

**R4a** (`configs/ppo_phase4_scratch_r4a_zeroobs.yaml`): regenerate the missing zero-obstacle source checkpoint from scratch under the FIXED physics: phase 4's full task/insertion predicate with `num_obstacles`/`obstacle_min`/`obstacle_max` forced to 0 via `cfg_overrides`, `ent_coef: 0.008`, 3M steps. The idea: isolate whether obstacles were really the blocker by removing them entirely, on the simplest possible version of this task under the corrected grasp physics.

**R4a result: also stalled, killed at about 2.9M/3M.** `ever_grasped_rate` stayed at 0.000 at every checkpoint checked (1.5M, 2.4M), `collision_rate` 0.000 throughout as expected (no obstacles to hit), episodes running the full 400 steps every time (no early termination at all, the opposite failure mode from R3, and grasping *still* never happened). The one new, useful signal: `std` (action noise) collapsed hard late in training (0.99 at 1.5M -> 0.89 -> 0.56 at 2.4M) while `ever_grasped` stayed flat at zero and `entropy_loss` shrank alongside it: the policy converged to a confident, low-exploration behavior without ever discovering the admissible grasp band, the specific "entropy starvation" pattern flagged in an external second-opinion discussion of this problem. Killed once that trend was unambiguous; R4b (warm-start the obstacle curriculum from R4a) was never launched since R4a produced no working grasp policy to warm-start from.

**Where this leaves things after R1/R2/R3/R4a (four independent training configurations, all from scratch, all under the E79-fixed physics, all stalled on cold-start grasp acquisition):** obstacles are very unlikely to be the primary blocker: R4a removed them entirely and still got 0.000. The admissibility band's exact width is very unlikely to be the primary blocker either: R2 widened it substantially with zero effect. What's common to all four and still untested: `grasp_shape`'s dense reward (`rewards.py`) is Euclidean distance to the peg's CENTER, which is the one point the E79 admissibility gate always rejects (the gate requires 1.5-5.5cm axially above center), and every one of these runs was being pulled, by the strongest available gradient, toward a point that can never satisfy the gate. Re-centering that reward term on the admissible band itself, rather than on the peg's center, is the one concrete, still-untried lever this investigation converges on. Not yet attempted: a decision point, not a conclusion, as of this entry.

**A cheap check that reframed the whole question**, run on R4a's own checkpoints rather than launching new training: split eval into a pre-grasped start (peg free in-hand at t=0, bypassing cold-start grasp acquisition entirely, zero obstacles) versus the real cold-start condition, at a checkpoint (900k) where the pre-grasped starting distribution was still in-training-distribution (not a late, stale checkpoint). Result: **identical**, 0.017 success / 0.0010 depth in BOTH conditions. Giving the policy a completely free grasp bought nothing. That rules out "grasp acquisition is the bottleneck" as the explanation for the overall flat-zero success rate. The thing that's actually unsolved is narrower and different: insertion precision itself, independent of grasp acquisition or obstacles. Consistent with the oldest fact in this whole investigation: the privileged scripted oracle (zero exploration problem) only ever hit 2-6% on insertion, and needed an active reorientation strategy for the top of that range.

**R5** (`configs/ppo_phase4_r5_insertonly_scratch.yaml`): isolates insertion precision directly, prompted by that split. `cfg.insert_only` (every episode starts already grasped+xy/tilt-aligned directly in the insertion zone, `env._start_pre_inserted`, reused machinery, not new: this is E33/E37/E73's own task), `num_obstacles` forced to 0, `insert_start_depth_curriculum` 1.0->0.0 over 50% of training (eval always forces the real depth=0 case regardless of training curriculum state, so every checkpoint's eval number is genuine, never diluted). What's actually new vs every prior insert-only attempt: **from scratch**, not warm-started (every earlier insert-only run, including E73, was warm-started from phase 3's E24), and zero obstacles (every earlier insert-only run kept the full 2-5 range). `ent_coef: 0.01`, `max_steps: 80` (proven value, no reach/grasp/transit legs to cover).

**R5 final result: a genuine, new best for the insertion sub-task.** Full checkpoint sweep (100 episodes each, real depth=0 condition, eval settings matched to training's `max_steps: 80`):

| steps | 250k | 500k | 750k | 1.0M | 1.25M | 1.5M | 1.75M | 2.0M | 2.25M | 2.5M (final) |
|---|---|---|---|---|---|---|---|---|---|---|
| success | 0.060 | 0.070 | 0.090 | 0.050 | 0.100 | 0.070 | 0.080 | 0.020 | 0.090 | 0.080 |

Plateaus from 750k onward: mean 0.073, std 0.024 across those 7 checkpoints, and the expected pure sampling noise at n=100 episodes and this success rate is a std of about 0.027, essentially the same number. The checkpoint-to-checkpoint swings (including the 2.0M reading that looked like a possible regression mid-run) are fully explained by ordinary n=100 binomial variance, not real training instability or decay, confirmed by finishing the sweep rather than reacting to any single checkpoint. `std_per_dim` (action exploration noise) climbed substantially over the run (roughly 1.25 at 250k to 2.6-3.3 at the final checkpoint) without success degrading, unlike R1/R4a's entropy-starvation signature where shrinking std coincided with zero progress. Here rising exploration noise coexisted with a stable, elevated success plateau instead.

**This roughly doubles E73's 0.040 (the previous standing-best real number in the entire KUKA phase-4 investigation, itself warm-started with obstacles present) with a from-scratch, zero-obstacle, otherwise-comparable recipe.** `tilt` also improved over the run (24.4deg at 250k down to about 21-22deg by the end) though remains well above the oracle's 2.5deg (with active reorientation), and there is room left in this specific sub-task, not just noise to explain away.

**What this does and doesn't establish, stated plainly**: this confirms insertion precision is learnable by RL here at a meaningfully higher rate than anything seen before, a useful new fact. It is still a SUB-TASK result (pre-grasped, zero obstacles, `max_steps: 80`, not the full reach-grasp-avoid-align-insert chain), and it does not by itself move the full-task success rate, which stayed at the historical about 0.015-0.02 floor throughout this entire investigation (R1/R2/R3/R4a). Composing this with a working reach+grasp+obstacle-avoidance policy (via `scripts/evaluate_composed.py`'s existing Task1->handoff->Task2 mechanism, and a fresh from-scratch Task-1/`align_only` run under the E79 physics, neither of which has been attempted yet) is the identified next step, not yet taken as of this entry.

## E81: H3's observation-widening broke reproducibility of the adopted checkpoints, reverted

While re-recording the four demo videos in `media/`, `evaluate.py` and `record_rollout.py` both refused to load `runs/phase1_ppo`, `runs/phase2_ppo`, `runs/phase3_ppo_best`, and `runs/phase4_full_dream`: "spaces must have the same shape". Cause: H3 (introduced during the R1-R5 investigation above, see `manipularl/env.py`'s prior `_assemble_obs`) had widened every phase's observation from 123 to 131 dims/frame, appending peg tilt, ring distance, a shaped depth signal, the peg-tip-to-hole vector, and ring contact. That applied to all six phases, not just Phase 4, because they all share one environment class, so it silently broke every checkpoint trained before it, including all four checkpoints this report's headline numbers are drawn from.

First tried `train.py`'s own `warm_start_pad()` (the function-preserving weight-transplant already used elsewhere in this project) to make the old checkpoints loadable again without retraining. Verified the padded network is bit-identical to the original (`torch.allclose`, max diff 2.5e-7, on random inputs). But the padded Phase 1 checkpoint still only scored 0.36 in a real rollout, not the reported 1.00. Mean episode length went from 11.3 steps to about 150, with a big rise in joint-limit penalty steps. The most likely explanation: several of H3's new fields (ring distance, peg-tip-to-hole, ring contact) are only well-defined when a hole actually exists (`use_hole=True`, Phase 4 only); for Phases 1-3 (`use_hole=False`) they are computed against undefined hole geometry and can be NaN. A padded network's new-dim weights are exactly zero, so `0 * finite_value = 0` as intended, but `0 * NaN = NaN`, and that NaN would propagate through the fully-connected first layer into every hidden unit, corrupting the whole forward pass regardless of the old, legitimate dims' values. The random-input equivalence test never caught this because it never sampled NaN.

**Fix: reverted, not padded.** Pulled H3's 8 appended fields back out of `_assemble_obs` into `manipularl/obs_h3_extras.py` (`h3_extra_dims(s)`, not called by default), keeps the code for anyone who wants to deliberately reintroduce it later (with a matching retrain, as several post-H3 Phase 4 configs already did), without it silently riding along in the shared environment class. `env.py`'s live observation is back to 123 dims/frame, matching what `README.md` already documented. Deleted the throwaway padded-checkpoint artifacts. Re-evaluated all four adopted checkpoints directly, no surgery:

| phase | before revert (padded, broken) | after revert | originally reported |
|---|---|---|---|
| 1 | 0.36 | **1.000** | 1.00 |
| 2 | 0.06 | **0.995** | 0.995 |
| 3 | 0.15 | **0.86** / 0.08 collision | 0.80 / 0.175 collision |
| 4 | 0.01 | **0.015** | 0.015-0.02 |

Phases 1, 2, and 4 reproduce almost exactly. Phase 3 comes back *better* than originally reported (0.86/0.08 vs. 0.80/0.175), plausibly because the original 0.80/0.175 number was itself measured after H3 had already partially contaminated something in Phase 3's eval path (Phase 3 is `pick_place`, also `use_hole=False`), though this wasn't confirmed further since the direction of the discrepancy isn't concerning. ## What actually solved phase 2 (E5 to E7)

1. Diagnose before guessing. Splitting the task into approach/grasp/carry/release and testing each in isolation showed the real problems: the arm never even approached the peg cold, and it rarely released properly either.
2. The phase 1 warm start was actively hurting. Phase 1 teaches "reach toward goal_pos," but in phase 2 that's the place target, not the peg, so the warm-started policy kept driving toward the wrong thing and PPO couldn't unlearn it fast enough.
3. From scratch, with shaping and an annealed grasp curriculum, actually worked. Nothing was fighting the "move toward peg" signal anymore, the release-pressure term fixed the last step, and the curriculum forced cold-start grasping to develop while carry/release was already solid.

## How to reproduce things

```bash
# the solved phase 2:
python train.py --config configs/ppo_phase2_scratch.yaml --out-dir runs/phase2_ppo
python evaluate.py --run runs/phase2_ppo --phase 2 --episodes 200
python scripts/diagnose_phase2.py --run runs/phase2_ppo --mode coldstart
python scripts/diagnose_phase2.py --run runs/phase2_ppo --mode pregrasped

# the phase 3-5 chain, warm started:
bash scripts/chain_p3p4p5.sh

# the demo/BC backstop, kept for completeness, not needed for phase 2:
python scripts/scripted_expert.py 40
python scripts/collect_demos.py --episodes 500 --out runs/demos_phase2
python scripts/bc_pretrain.py --demos runs/demos_phase2 --out runs/phase2_bc

# the soft warm-start A/B:
python train.py --config configs/ppo_phase3.yaml --out-dir runs/phase3_ppo_soft \
 --warm-start runs/phase2_ppo/model.zip --warm-start-norm runs/phase2_ppo/vecnormalize.pkl \
 --soft-warm-start --soft-log-std -0.7
```

## Where the logs live

Per-run stdout is `runs/<name>.log`, TensorBoard scalars are under `runs/<name>/tb/`, periodic checkpoints under `runs/<name>/checkpoints/`, and the best-by-eval-reward model under `runs/<name>/best/`. A few orchestration logs cover multiple entries: `runs/overnight.log` (E2, E4), `runs/fallback.log` and `runs/scratch_p2.log` (E6, E7), `runs/chain_p3p4p5.log` (E9-E11), `runs/soft_p3.log` (E12), `runs/collect_demos.log` (E8).
